# JalVaani dashboards (`dev/`)

There are two views:
- **farmer**: one district on a phone, in plain words;
- **government**: all 36 districts, a map, priorities, and data gaps.

Both work in **English, मराठी and हिन्दी**. A site guide (chatbot) answers questions and shows people around the site.

The site uses the project's real data and model outputs only. It never changes them.

```
dev/
├── pipeline/build_dashboard_data.py   reads data/ and 04_results/ (read-only) → writes dev/backend/data/
├── backend/                           FastAPI: data API, chat (Groq or offline guide), speech endpoints (Gnani, later)
│   ├── app/main.py                    every endpoint
│   ├── app/services/                  store (read-only data), advisories (farmer tips), priorities (government rules),
│   │                                  chat, speech/ (provider interface + Gnani skeleton)
│   ├── app/chat/                      site_guide.md (what the assistant knows), faq.json (offline guide, 3 languages)
│   ├── data/                          GENERATED by the build script (git-ignored)
│   ├── tests/                         pytest: API, rules, "the build never touches project data"
│   └── .env.example                   GROQ_API_KEY, GROQ_MODEL, GNANI_* (copy to .env; never commit .env)
├── frontend/                          React + Vite + TypeScript + Tailwind; Recharts (charts), Leaflet (map), i18next
│   └── src/i18n/{en,mr,hi}.json       every text on the site; districts.json = district names in Marathi / Hindi
├── scripts/                           setup.ps1, build_data.ps1, run_local.ps1
└── docs/                              ARCHITECTURE, DATA_CONTRACT, HMI_CHECKLIST, CHATBOT, SPEECH_PLAN, I18N_REVIEW
```

## Run it locally

You need Python 3.11+ and Node 20+. Both are already on this laptop.

```powershell
# once
powershell -ExecutionPolicy Bypass -File dev\scripts\setup.ps1      # packages + builds the data

# every time
powershell -ExecutionPolicy Bypass -File dev\scripts\run_local.ps1  # → open http://localhost:5173
# or, as one server on :8000 (built frontend):
powershell -ExecutionPolicy Bypass -File dev\scripts\run_local.ps1 -Single
```

Tests:
- backend: `cd dev\backend; python -m pytest`
- frontend: `cd dev\frontend; npm test` and `npm run build`

## Do we need to host the model?

**No, not for now.** The model runs in **batch** on Colab, using the `09_tft_colab_production_v4_3.ipynb` notebook. It writes `dashboard_export/`, which holds:
- the latest forecast;
- the backtests;
- per-district accuracy.

The build script turns those files into the dashboard data. The backend only *reads* files, so no model server is needed.

**Refreshing the site when new data comes in:**
1. CGWB publishes newer groundwater readings.
2. Run the collectors and preprocessing (see the root `README.md`).
3. Upload the new `data/master/master_dataset_v4target.csv` to the v4.3 notebook on Colab and run it.
4. Unzip `tft_v4_3_outputs.zip` into `04_results/tft_v4_3/`.
5. Run `dev\scripts\build_data.ps1` and restart the backend.

Until a v4.3 run exists, the site shows the v4.2 backtests and accuracy, and says honestly that the latest forecast has not been produced yet. It never shows placeholder numbers.

**Hosting later (not needed for the project demo):**
- one small Linux VM, or a platform such as Render or Railway;
- `npm run build`, then `SERVE_FRONTEND=1 uvicorn app.main:app` behind HTTPS;
- the `.env` keys set as server secrets;
- the model stays a batch job.

A further step, only if forecasts must refresh without Colab, is a CPU "inference bundle". It would hold:
- the saved networks;
- the scalers;
- the seasonal tables;
- the post-processing parameters.

New readings could then be forecast without retraining.

## Rules this folder keeps (so the model can never be affected)
- **Nothing in `dev/` writes outside `dev/`.** A test checks that `data/`, `04_results/` and `03_models/` are unchanged after a build.
- **The model pipeline never reads `dev/`.**
- **No mock data.** Every number comes from a real file. Where data is missing, the site says so. See `docs/DATA_CONTRACT.md`.
- **Test-only synthetic records live in the tests.** They are named `synthetic_*` and the app never loads them.

## Chatbot and voice (keys go in `dev/backend/.env`, see `.env.example`)
- **Chat.** With `GROQ_API_KEY` set (optionally also `_2`, `_3`, which are used in turn when one is rate-limited) and `GROQ_MODEL=qwen/qwen3.8-27b`, the guide is an LLM assistant. Without a key it is an offline three-language guide. See `docs/CHATBOT.md`.
  - Tested live on 2026-10-31: Marathi answers using only the numbers on screen; a borewell question in Hindi was referred to officials.
- **Voice (Gnani Vachana).** **One** `GNANI_API_KEY` covers speech-to-text and text-to-speech, and the endpoints are built in. With the key set:
  - the 🎤 button appears in the chat;
  - "Listen" reads cards aloud.

  Tested live on 2026-10-31: a Marathi round trip, text → speech → text, word for word, in about 0.9 s each way. See `docs/SPEECH_PLAN.md`.
